# Plane (Community Edition)

Project management: issues, cycles, modules, pages and a collaborative editor,
with public project pages for anything you want to share. Upstream:
[makeplane/plane](https://github.com/makeplane/plane).

It is the third project management stack here, and the largest of them.
[`business/vikunja`](../vikunja/) is two services and does tasks;
[`business/openproject`](../openproject/) is the enterprise shape with Gantt
and work packages; this is the Jira-alternative shape, at thirteen services and
about 1.4 GiB at rest.

> **Object store: Silo.** MinIO withdrew its public container images on
> 2026-09-24. The object store here is [`pgsty/silo`](https://github.com/pgsty/silo),
> a maintained MinIO fork published under release tags — the image upstream's own
> compose names since v1.4.3. It reads
> MinIO's variables and answers on the same port, so the service keeps the name
> `plane-minio` and nothing that talks to it changes. A data directory written
> by the old MinIO image was not tested against it — see [`UPSTREAM.md`](UPSTREAM.md).

Project, source, licence and origin: [`UPSTREAM.md`](UPSTREAM.md).

## Architecture

```text
Traefik ──http──→ plane-proxy :80          Plane's own Caddy, the only routed service
                       │
                       ├── /              → plane-web     the application
                       ├── /spaces/       → plane-space   public project pages
                       ├── /god-mode/     → plane-admin   instance administration
                       ├── /live/         → plane-live    the collaborative editor
                       ├── /api/ /auth/   → plane-api     Django and gunicorn
                       └── /uploads/      → plane-minio   attachments
                                                │
        plane-worker, plane-beat-worker ────────┤
                                                │
              plane-db · plane-redis · plane-mq ┘   all app-internal
```

Keeping Plane's own proxy as an internal hop is what keeps Silo and the four
interfaces off `proxy-public`: Traefik talks to the proxy, and the proxy talks
to them.

## Claim /god-mode first

```bash
cp .env.example .env            # host name
ops/init.sh                     # eight secrets, and the two connection URLs
sudo chown -R 1000:1000 volumes/redis volumes/uploads volumes/logs
docker compose up -d            # the migrator runs first; give it a few minutes
```

Then, before anyone else can reach the host name:

1. Open `https://<your host>/god-mode`. **The first visitor becomes the
   instance administrator.** There is no password in front of it and no setup
   token — whoever arrives first owns the instance.
2. Close sign-up. It is open by default; measured on a fresh install, the
   instance API reports `enable_signup: true`.
3. **Switch telemetry off.** Every six hours Plane sends the instance domain
   and every workspace slug to `telemetry.plane.so`. There is no environment
   variable for it — it is an instance setting, so this is the only place to
   change it.

`access-vpn` is what makes steps 1 to 3 survivable rather than a race.

## Security model

- **Eight Docker Secrets.** Upstream's defaults are `plane`/`plane` for
  PostgreSQL and RabbitMQ and `access-key`/`secret-key` for Silo. All eight
  are generated by `ops/init.sh`, and `config/entrypoint.sh` exports them
  because Plane reads everything from the environment and has no `_FILE`
  variant for any of it.
- **Nothing publishes a port.** Upstream's proxy publishes 80 and 443; here
  Traefik is the only way in, and Silo, the API and the three interfaces are
  on an internal network.
- **Non-root everywhere it works.** Every Plane image declares root. The
  backend runs as uid 1000 — the image makes `/code` world-writable, which is
  how it works at all — and so do Valkey and Silo. The nginx and Caddy images
  keep root and get the capability each needs, no more.
- **`CORS_ALLOWED_ORIGINS` is set** to the host name; upstream leaves it empty.
- **Webhooks reach anywhere by default.** `APP_WEBHOOK_ALLOWED_HOSTS` is empty,
  which means no restriction. A webhook is an outbound request the application
  makes on a user's behalf — worth narrowing to the hosts you integrate with.
- **OIDC and SAML are not available.** They are in the paid editions, which are
  a separate codebase. What this build has is email and password, plus the
  social logins you configure in `/god-mode`.

## Known limits

- **`limit-standard` is not measured against this interface.** Plane is a
  code-split single-page application, and the two comparable stacks that *were*
  measured — Twenty and Windmill — both exceeded the standard bucket on their
  first load. If the interface half-renders, the rate limit is the first thing
  to look at; `limit-extra-large` exists for exactly this shape.
- **Little has been used.** One workspace, one project, one work item and one
  image attachment stored in Silo and read back; no second browser in the live
  editor, no import or export.
- **The worker idles at 638 MiB**, the largest single service here. An export
  or an import goes through that process, and no such job has been run.
- **Thirteen services is the cost.** About 1.4 GiB at rest before anyone opens
  a project.
- **No backup of Silo has been restored**, only described below.
- **Nothing here has run behind this repository's Traefik yet.**

## Backup

| | |
|---|---|
| **Everything structured** | `./volumes/postgres` — projects, issues, cycles, comments, users. Dump it: `docker compose exec plane-db sh -c 'pg_dump -U plane plane' > plane.sql` |
| **Attachments** | `./volumes/uploads` — Silo's data. Not in the database, and not reconstructible |
| **The keys** | `.secrets/secret_key.txt` signs sessions and password-reset links; `.secrets/aws_secret_access_key.txt` is what the backend authenticates to Silo with. Restoring the volumes without them leaves data nothing can read |
| **Reproducible** | `./volumes/redis`, `./volumes/rabbitmq`, `./volumes/logs`, `./volumes/proxy-*` |
| **Quiescing** | `pg_dump` is consistent on its own. Stop the stack before copying `volumes/uploads`, or an upload in flight lands half-written |

```yaml
# /etc/borgmatic/config.yaml
source_directories:
  - /srv/secure-docker-blueprint/business/plane/volumes/uploads
```

Restore: put the volumes back with `redis`, `uploads` and `logs` owned by
`1000:1000`, restore the secrets, start the database, load the dump, then bring
the rest up. The migrator runs again and finds nothing to do.

The Plane images carry CRITICAL findings that have published fixes: `plane-live` and `plane-space` 4 each in Node packages (storybook and tinypool, development tools the server does not run, and `proxy-addr`), `plane-backend` 1 in PyJWT (CVE-2026-102268), and `plane-proxy` 1 in Alpine's brotli (CVE-2026-111497). v1.4.3 is the newest stable Plane release.

**Risk:** `proxy-addr` affects only trusted-proxy entries written in IPv4-mapped IPv6 form; whether Plane's token handling is affected by the PyJWT flaw has not been checked. Keep the stack behind the proxy and watch for the next release.

The PostgreSQL image, `postgres`, carries one CRITICAL finding, CVE-2025-68121, in the Go runtime of `gosu`, the helper that drops root privileges at start. Every current image of this line ships the same gosu build, and its maintainer has not rebuilt it with a fixed Go.

**Risk:** the flaw is in TLS session resumption, and gosu opens no network connection, so it is not reached. The finding clears when upstream ships a rebuilt gosu.

The RabbitMQ image carries one CRITICAL OpenSSL finding, CVE-2026-31789. The application has not documented support for RabbitMQ 4, the only line that is still rebuilt, so the broker stays on the last 3.x release.

**Risk:** the flaw affects only 32-bit platforms. Keep the broker on the internal network.
