already settled, what a lab run still has to show, and how the work is divided
between coordination, the host bootstrap and the lab run. The test plan itself
is [`docs/host-verification-ingress.md`](../../host-verification-ingress.md);
it is authoritative, and this page does not restate its rows.

**No concrete lab data in this repository.** The lab host, its addresses, its
names, the DNS zone, the hoster, the upstream firewall and every credential are
kept outside the repository and handed over out of band. This page, the plan,
the results and every commit message name them by role only (see
[Public content](../../standards/commit-rules.md#public-content)).

## 4. Technical points a lab run has to know

- **Bindings.** `TRAEFIK_BIND_V4` and `TRAEFIK_BIND_V6` have no default;
  `render.sh` and `validate.sh` refuse `TRAEFIK_BIND_V4` unset. An empty value
  publishes nothing for its family. Both are rendered into
  `config/published-ports.yml`.
- **`COMPOSE_FILE` decides the shape.** It must name `network-dual-stack.yml`,
  `config/published-ports.yml` and `config/edge-networks.yml`. A `docker
  compose` call without the overlay tries to recreate `proxy-public` as
  IPv4-only.
- **Daemon prerequisites** before the dual-stack network exists: `ipv6`,
  `ip6tables`, `userland-proxy: false` (`core/traefik/docs/ipv6-dual-stack.md`).
  An existing IPv4-only `proxy-public` is not changed in place.
- **`PUBLIC_NETWORK_SUBNET_V6`** — the example's prefix is refused; generate a
  ULA prefix as the IPv6 guide shows.
- **The endpoint** of the published ports is Traefik's address on
  `proxy-public` (`gw_priority: 100`); IPv4 is measured in the lab, IPv6 is E3.
- **`TRUSTED_RANGES`** ships empty; block A declares the lab's LAN range for
  its duration only.
- **Edge networks** — a stack not listed in `EDGE_NETWORKS` is unreachable
  without a log line; each Traefik recreate interrupts every stack for about
  seven seconds (measured in step 8, accepted, DEC-075 addendum 2026-11-02); a
  default daemon offers 32 user networks.
- **The host ruleset** (`inet blueprint_ingress`) is installed by the operator,
  never by the repository, from a session over the VPN, with the five-minute
  way back of `core/traefik/docs/host-firewall.md`. The CrowdSec tables stay
  untouched.
- **The exposure test** runs from a machine off the VPN. Behind a CDN proxy it
  is given the origin address, never the proxied name. Whatever filters in
  front of the host is part of what it measures. The marker is one
  measurement, repeated after a change of bindings, proxy mode or firewall.
- **The whoami routers per policy** are a test-only
  `docker-compose.override.yml`, removed after block A.
- **IPv6-only egress** — registries and sources without AAAA need NAT64/DNS64
  or an excluded path (audit §3.4).

## 5. Migration and rollback

| What | Forward | Back |
|---|---|---|
| `core/traefik/.env` from `v0.9.5` (B) | `scripts/migrate-traefik-env.sh core/traefik` as a dry run, then `--write`; it writes `.env.pre-model` and refuses a file that already has one | stop Traefik, restore `.env.pre-model`, check out `v0.9.5`, `up -d`; the published state equals the one saved before |
| Shared installation → edge networks (N) | per stack: list in `EDGE_NETWORKS`, render, `up -d` Traefik; `TRAEFIK_NETWORK=<project>-edge`; `up -d` the stack; `validate.sh --strict` | per stack, stack first: `TRAEFIK_NETWORK=proxy-public`, `up -d` the stack; then its network out of `EDGE_NETWORKS`, render, `up -d` Traefik; `validate.sh --strict`; `docker network rm <project>-edge` once unused |
| Docker daemon settings | back up `/etc/docker/daemon.json`, apply, restart | the IPv6 guide's "Rollback" |
| Host ruleset (F) | `nft -c`, install, load with the timed way back, cancel the way back once the session survives | `nft delete table inet blueprint_ingress`; the timed way back does it unattended |

Every forward step records the state before it (`docker port traefik`,
`ss -ltnp`, `nft list ruleset`, `docker network inspect`); every rollback is
shown by comparing against that record.

## 6. Who does what

Three roles, kept apart. None of them works on a production host.

| | Coordination | Host bootstrap | Lab run |
|---|---|---|---|
| Purpose | the integration branch; review of incoming lab pull requests against the decisions; the plan and PR #308 kept consistent; the final security, quality and release review | secure the lab host once, before anything else runs on it | run the plan's open rows and record the results |
| Host access | none | root, once | an unprivileged account with key-only SSH and `sudo`, from the operator's workstation |
| Writes to the repository | the integration branch, the decision records, the release preparation | nothing | its own lab branch only |
| Ends with | PR #308 ready for the maintainer's merge decision, or the rows still open | a host with an administrative account, key-only SSH, root login off, the hoster's console tested once, and a record of what was changed — kept outside the repository | a report back to coordination (section 8) |

The bootstrap deploys no blueprint stack and copies no credential into a
checkout. The lab run holds credentials only in the host's `.env` files and
in the operator's own store; a DNS credential is scoped to the lab zone.

## 7. Git and pull requests

- **One integration branch.** `feature/ingress-step-8-host-evidence` collects
  every result, correction and documentation change of step 8. `dev` stays
  unchanged until step 8 is complete; PR #308 stays open against `dev`, as a
  draft, until then.
- **The lab run works on its own short-lived branch**, cut from the
  integration branch and named `lab/ingress-step-8-<short-name>` (for example
  `lab/ingress-step-8-execution`). Its finished, reviewed changes go to the
  integration branch as a pull request against
  `feature/ingress-step-8-host-evidence`, opened as a draft.
- **One writer per branch.** The lab run pushes only to its lab branch;
  coordination pushes only to the integration branch. After a lab pull request
  is merged, coordination updates the integration branch and checks the
  integration; a further lab branch is cut from that state.
- **Merges.** No pull request — a lab pull request or PR #308 — is merged by
  anyone but the maintainer, and auto-merge stays off.
- Results go into the "Results" table of `docs/host-verification-ingress.md`
  and into a run report beside this page,
  `docs/labs/ingress/<yyyy-mm-dd>-results.md`. A correction found in the run
  is its own commit, one logical change each.
- [`docs/standards/commit-rules.md`](../../standards/commit-rules.md) binds:
  each commit and each push is asked for first; English only; roles, never
  names or addresses; the private-names check against the staged diff before
  every commit; `docker compose config` output redacted.
- **A push publishes the whole history it carries**, on a temporary branch as
  much as on any other. Before every push, every commit not yet on the remote
  is checked — content and commit message — against the public-content rule
  and the private-names check (`git log -p @{upstream}..HEAD`, or
  `git log -p <integration branch>..HEAD` for a new branch). A later commit
  that removes a leak does not undo it: the commit that carries it is
  rewritten before the push.

## 8. What comes back to coordination

The run report, on the lab branch, holds:

- the commit under test and the lab host's shape by role (dual-stack, profile,
  stacks installed, auth postures in use);
- per open row: date, result (`pass`, `fail`, `not run` with reason) and the
  evidence, redacted;
- every deviation from the plan and why;
- every correction, with its commit;
- what was changed on the host and not reverted.

Coordination assesses the report, updates the host verification of DEC-063
and DEC-075–DEC-078, decides which gates are met, and prepares the release.
