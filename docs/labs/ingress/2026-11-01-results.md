## Deviations from the plan

- **X1 in two runs, one per address.** The first external run used the script
  before `8f19db3` and measured nothing valid. With `8f19db3` the operator ran it
  from OUT once against H1's IPv4 address and once against its IPv6 address;
  both held the `direct` profile. A run from the host against itself was not
  counted. `validate.sh` reads the last marker line of
  `config/exposure-verified`, so both lines are kept in the file, IPv4 first.
- **A9.** The plan expects 403 over `[::1]`. With `userland-proxy: false` Docker
  does not forward the IPv6 loopback address to a container, which
  `core/traefik/docs/ipv6-dual-stack.md` states; the connection times out. The
  gate is not bypassed — over the host's global IPv6 address and over
  `127.0.0.1` the answer is 403. The expected value of A9 contradicts the
  documentation.
- **N and G4 without a VPN.** Every policy but `access-public` refuses the
  host's own requests, and 403 from the access middleware proves nothing about
  the backend. The probes therefore used test-only routers with
  `Host(…) && ClientIP(<gateway of proxy-public>)` and `access-public`: only the
  host itself matches, every other client gets 404. G4 ran on Heimdall's own
  router with that rule and `access-public` for its duration, so the basicAuth
  gate is what answered.
- **N2, step 4 of the first move** was skipped by the lab's helper script (it
  stopped on the expected exit 1 of `--strict` while the marker is open); N4
  ran it afterwards.
- **Rows not run in this phase:** the TS and LAN columns of A, A8, F1–F9, M2,
  G5–G7, S2, X4 and O. F stays open by decision: the rendered ruleset
  admits management from the VPN ranges only, and without a VPN loading it
  would close SSH over the public address.

## Findings

1. **A Traefik recreate interrupts every stack for about seven seconds** (N2,
   N5). Measured with a probe every 0.2 s against three stacks: from the stop
   signal Traefik accepts no new connection; the old container needs 3.3–4.8 s
   to exit and the new one 1.6–2.0 s to start, 6.5–7.3 s in all. The "about two
   seconds" of the 2026-10-31 lab run (DEC-075, `edge-networks.md`) covers the
   start alone, and "the other stacks stay served" in step 1 of "Moving a shared
   installation" does not hold: they are interrupted for the recreate. `edge-networks.md`
   and `.env.example` now state the measured figures. The moved
   stack is unreachable in addition until its healthcheck passes (Traefik skips
   a starting container): about 5 s for httpbin and it-tools, under 1 s for
   whoami, which has none.
2. **Moving back, list first, cuts the stack off between step 1 and step 3**
   (N5): "Moving back is the same steps with the old value" shortens
   `EDGE_NETWORKS` and recreates Traefik before the stack leaves its edge
   network. Moving the stack to `proxy-public` first and shortening the list
   afterwards keeps the interruptions apart and short — measured for whoami: its
   own recreate 2.3 s, then Traefik's 4.5 s, against one stretch of about 14 s
   list first for a stack with a healthcheck. `edge-networks.md` now describes
   the way back in that order.
3. **A removed edge network stays on the host.** Traefik's Compose project no
   longer names it, and nothing removes it; on a default daemon it keeps using
   one of the 32 address pools until `docker network rm`.
4. **v0.9.5 in the IPv4-only shape maps the published ports to
   `crowdsec-security`** (B1): the measurement behind step 2, on a host. In the
   dual-stack shape v0.9.5 already landed on `proxy-public`, the only network
   with both families.
5. **Automated scans began within two minutes of the first certificate.**
   Requests to the test zone's base name, which no router serves: one source
   sent about 1 270 requests in 16 seconds (`.env`, `.git/config`, WordPress
   paths), all answered 404, as were the others. No request from outside reached
   a closed router. A request no router matches meets no rate limit — the limits
   are positions of a router — and CrowdSec was not installed; `validate.sh`
   names that layer as absent with its residual risk. The access log records no
   request headers, so a browser and a scanner cannot be told apart in it.
6. **DNS-01 under a wildcard CNAME.** The test zone carries `*.<zone>` as a
   CNAME to the base name, so `_acme-challenge.<zone>` resolves through it and
   the ACME client set its TXT record on the base name. Issuance worked and the
   record was removed afterwards; a property of the test zone, not of the
   blueprint.
7. **Traefik 3.7.17 warns at start that `aliasHeadersStrategy` is unset**, once
   per entrypoint — recorded as expected in `core/traefik/UPSTREAM.md`.
8. **The CI tests read the host they run on.** The fixtures named the
   deployment's container, `traefik-core`, and `validate.sh` inspects the
   running container of that name: on the lab host the suite measured the lab's
   Traefik. With the N4 correction ten tests failed there for that reason alone;
   the fixtures now use a name no deployment uses. A runner without a Traefik
   container was never affected.

## CrowdSec on the entrypoint

Not rows of the plan; `core/crowdsec` is one of its prerequisite stacks, verified
here as its README, `docs/appsec.md` and `docs/profiles.md` describe it. The
firewall bouncer was not installed: no automatically filled rule may reach the
management path, and without a VPN that path is SSH over the public address.

| Check | Result |
|---|---|
| Engine | `v1.7.8` healthy on `crowdsec-security` only; LAPI published on 127.0.0.1 only; the Traefik access log read and parsed |
| Bouncer | key from `cscli bouncers add`, switch on, render, `--force-recreate`: the plugin `v1.7.1` loaded and pulled from the LAPI within a second of the start |
| Ban, per family | a `cscli decisions add` for the source of each family answered 403 on `w-public` after 30 s (stream interval 60 s); lifted after 59 s |
| AppSec | `CROWDSEC_APPSEC_ENABLED=true`, render, `--force-recreate`: the virtual-patching rule answered `/.env` with 403 on both families; SQL injection, path traversal and script patterns passed — the shipped rule sets carry no Core Rule Set, as `appsec.md` states |
| Fail-open | with the engine stopped every request passed, `/.env` included, with no added latency; after the restart the rule answered 403 again |

**Finding: `validate.sh --strict` reads the configuration, not the running
static configuration.** After the switch and a plain `docker compose up -d` —
which does not recreate Traefik for a change of the bind-mounted
`config/traefik.yml` — `--strict` exited 0 and reported the entrypoint bouncer
present while the running Traefik had no plugin and no bouncer had pulled. The
README names `--force-recreate`; nothing reports the difference when it is
forgotten. For the published ports `validate.sh` does compare the running
container (PENDING); for the static configuration it does not.

`docs/appsec.md` said in its enable step that Traefik is not restarted and a
changed label recreates the application container — left from the router-label
model; corrected.

## Vaultwarden's access paths

`apps/vaultwarden` 1.37.4 with MariaDB 11.4, its SMTP pointed at `apps/mailpit`
on `proxy-public` — the shared network the Mailpit README names for a sending
stack. The client paths were driven through the API the Bitwarden clients use,
by a lab script that derives the keys as the clients do — no official Bitwarden
desktop, mobile, browser or CLI client was run, and those stay open — over a
test-only host router; the shipped router (`access-vpn`) answered 403 to
every other source for `/`, `/admin`, `/api/config` and the token endpoint.

| Path | Result |
|---|---|
| Registration | the e-mail token flow (`send-verification-email`, the token from Mailpit's API, `register/finish`); with signups off a new registration is refused, the existing account logs in |
| Login and sync | password grant on `/identity/connect/token`, `/api/sync`, an item created and synced; `/api/sync` without a token 401 |
| Notifications | WebSocket upgrade on `/notifications/hub` through Traefik: 101 with a token, 401 without |
| Admin panel | the Argon2 token: wrong 401, right a session that lists the account; without the session 401 |
| Headers | `X-Frame-Options: SAMEORIGIN` from Vaultwarden itself through `headers-application-owned` |

`/admin` shares the router of the client API. Behind `access-vpn` both are
closed alike; an installation that opens the vault for mobile clients opens
`/admin` with it, behind its token and rate limit alone. The README lists a
separate router for `/admin` as a TODO — a decision for coordination.

`core/authentik` 2026.5.7 with PostgreSQL 16 and Redis 7.4, SMTP pointed at
`apps/mailpit`. The setup window was kept closed: `access-vpn` until the admin
existed, then the shipped `access-public`. Logins were driven through the flow
executor API — the endpoints the browser UI calls — by a lab script; no browser
was run, so the UI itself stays open as a test.

| Check | Result |
|---|---|
| First-run setup | `/if/flow/initial-setup/` opened directly is refused in 2026.5 ("navigate to the root URL"); from `/` the setup flow ran and set the admin |
| Login | identification, password and the MFA validation stage; the stage accepted a TOTP code from a device set up for the test admin |
| G1 forward-auth | after the outpost's `authentik_host` was set: 302 to the login, the callback, `X-Authentik-Username` at whoami, the session cookie served the next request |
| G3 fail-closed | server stopped: 500 with and without a session, never 200 |
| E-mail | every `send_mail` task failed in the worker: it sat on `app-internal`, `internal: true`, where no SMTP host resolves. With the corrected compose file applied (the worker on `app-egress`, the database and Redis on `app-internal` alone, the worker not on `proxy-public`) the worker reached a public submission port and a throwaway relay addressed by the host's public address, and `ak test_email` was delivered to it |
| Configuration under test | `ghcr.io/goauthentik/server:2026.5.7` for server and worker; the deployment checkout on the lab commit that carries the corrected compose file; G1 and G3 repeated on it with the same result |

After the checks Authentik went back to `access-vpn` and the forward-auth test
route was removed; only block A's `w-public` stays public until block A is
complete. A sink on `proxy-public` is not reachable from the worker's network, so
Authentik's mail in the lab is not delivered to Mailpit — by the network design.

Findings, corrected in the stack's files: the worker joins `app-egress`, the
pattern `apps/nextcloud` documents ("Network exception"), so e-mail can leave;
the embedded outpost's `authentik_host` has to be set, or the forward-auth
redirect goes to `http://localhost/`; the setup starts from the root URL; the
README's `docker compose logs server` named no service (`authentik-server`) and
printed nothing; the known issue "setup URL public" now names the closed start
as its remedy. Traefik 3.7 warns once per forward-auth middleware that
`trustForwardHeader` is not configured — recorded, not changed.

**Vaultwarden's `/admin` on its own router.** Authentik's "Pattern 2" — a second
router with a higher priority on the path — separates it with the existing
model (a test-only router on the running stack, host-local requests and a
source outside the VPN policy; no VPN client was available): with `access-vpn` on a `PathPrefix(`/admin`)` router, `/admin` and
`/admin/…` answered 403 to a source the VPN policy does not admit while `/`,
`/alive` and the client API stayed on the main router. Whether the stack ships
that router — and with a closed policy, forward-auth or both — is coordination's
decision; the forward-auth variant was not run.
