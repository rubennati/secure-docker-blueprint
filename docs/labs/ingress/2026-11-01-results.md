## Deviations from the plan

- **X1 in two runs, one per address.** The first external run used the script
  before `8f19db3` and measured nothing valid. With `8f19db3` the operator ran it
  from OUT once against H1's IPv4 address and once against its IPv6 address;
  both held the `direct` profile. A run from the host against itself was not
  counted. `validate.sh` reads the last marker line of
  `config/exposure-verified`, so both lines are kept in the file, IPv4 first.
- **A9.** The plan expects 403 over `[::1]`. With `userland-proxy: false` Docker
  does not forward the IPv6 loopback address to a container, which
  `core/traefik/docs/ipv6-dual-stack.md` states; the connection times out. The
  gate is not bypassed — over the host's global IPv6 address and over
  `127.0.0.1` the answer is 403. The expected value of A9 contradicts the
  documentation.
- **N and G4 without a VPN.** Every policy but `access-public` refuses the
  host's own requests, and 403 from the access middleware proves nothing about
  the backend. The probes therefore used test-only routers with
  `Host(…) && ClientIP(<gateway of proxy-public>)` and `access-public`: the host
  matches, every client outside it gets 404. So does a container that calls the
  host's public IPv4 address — hairpin NAT rewrites its source to the same gateway
  (measured 2026-11-02, Nextcloud's container against Authentik's test router) — so
  "host-only" meant the host and its containers. From 2026-11-02 the lab's test
  routers admit `ClientIP(127.0.0.1/32) || ClientIP(::1/128)` instead, and the probes
  run in a container that shares Traefik's network namespace: no other container
  and not the host can present a loopback source — measured: the probe 200, the host
  404 over IPv4 and no connection over IPv6, a container through the public address
  404. The results taken earlier came from the host and stand; none relied on
  containers being kept out. G4 ran on Heimdall's own
  router with that rule and `access-public` for its duration, so the basicAuth
  gate is what answered.
- **N2, step 4 of the first move** was skipped by the lab's helper script (it
  stopped on the expected exit 1 of `--strict` while the marker is open); N4
  ran it afterwards.
- **Rows not run in this phase:** the TS and LAN columns of A, A8, F1–F9, M2,
  G5–G7, S2, X4 and O. F stays open by decision: the rendered ruleset
  admits management from the VPN ranges only, and without a VPN loading it
  would close SSH over the public address.

## Findings

1. **A Traefik recreate interrupts every stack for about seven seconds** (N2,
   N5). Measured with a probe every 0.2 s against three stacks: from the stop
   signal Traefik accepts no new connection; the old container needs 3.3–4.8 s
   to exit and the new one 1.6–2.0 s to start, 6.5–7.3 s in all. The "about two
   seconds" of the 2026-10-31 lab run (DEC-075, `edge-networks.md`) covers the
   start alone, and "the other stacks stay served" in step 1 of "Moving a shared
   installation" does not hold: they are interrupted for the recreate. `edge-networks.md`
   and `.env.example` now state the measured figures. The moved
   stack is unreachable in addition until its healthcheck passes (Traefik skips
   a starting container): about 5 s for httpbin and it-tools, under 1 s for
   whoami, which has none.
2. **Moving back, list first, cuts the stack off between step 1 and step 3**
   (N5): "Moving back is the same steps with the old value" shortens
   `EDGE_NETWORKS` and recreates Traefik before the stack leaves its edge
   network. Moving the stack to `proxy-public` first and shortening the list
   afterwards keeps the interruptions apart and short — measured for whoami: its
   own recreate 2.3 s, then Traefik's 4.5 s, against one stretch of about 14 s
   list first for a stack with a healthcheck. `edge-networks.md` now describes
   the way back in that order.
3. **A removed edge network stays on the host.** Traefik's Compose project no
   longer names it, and nothing removes it; on a default daemon it keeps using
   one of the 32 address pools until `docker network rm`.
4. **v0.9.5 in the IPv4-only shape maps the published ports to
   `crowdsec-security`** (B1): the measurement behind step 2, on a host. In the
   dual-stack shape v0.9.5 already landed on `proxy-public`, the only network
   with both families.
5. **Automated scans began within two minutes of the first certificate.**
   Requests to the test zone's base name, which no router serves: one source
   sent about 1 270 requests in 16 seconds (`.env`, `.git/config`, WordPress
   paths), all answered 404, as were the others. No request from outside reached
   a closed router. A request no router matches meets no rate limit — the limits
   are positions of a router — and CrowdSec was not installed; `validate.sh`
   names that layer as absent with its residual risk. The access log records no
   request headers, so a browser and a scanner cannot be told apart in it.
6. **DNS-01 under a wildcard CNAME.** Under a wildcard CNAME to the base name,
   `_acme-challenge.<name>` resolves through the CNAME, and the ACME client sets
   its TXT record on the CNAME's target. Issuance worked and the record was
   removed afterwards; a property of such a zone, not of the blueprint.
7. **Traefik 3.7.17 warns at start that `aliasHeadersStrategy` is unset**, once
   per entrypoint — recorded as expected in `core/traefik/UPSTREAM.md`.
8. **The CI tests read the host they run on.** The fixtures named the
   deployment's container, `traefik-core`, and `validate.sh` inspects the
   running container of that name: on the lab host the suite measured the lab's
   Traefik. With the N4 correction ten tests failed there for that reason alone;
   the fixtures now use a name no deployment uses. A runner without a Traefik
   container was never affected.

## OIDC between Nextcloud and Authentik: what a closed Authentik leaves

Investigated before any change of access; nothing was opened. The lab runs Authentik
on `access-vpn` (its example ships `access-public`) and Nextcloud on its edge
network.

| Leg | Who calls | What it needs |
|---|---|---|
| Authorize and Authentik's flow pages | the user's browser | Authentik's router admits the browser's source — on `access-vpn`, a VPN client |
| Discovery, token, userinfo, JWKS | Nextcloud's container (`user_oidc`) | Authentik's public name over https from a container |
| Logout | the browser | as the first leg |
| WebDAV, CalDAV, sync after the login | the clients, with an app password | Nextcloud only — Authentik is not called |

Measured on the host:

- Authentik builds the issuer and every endpoint from the request's host and
  forwarded scheme. Asked over the Docker network
  (`http://authentik-server:9000/…/.well-known/openid-configuration`) it answers
  `http://authentik-server:9000/…` for issuer, authorize, token, userinfo and JWKS;
  asked with the public name and `X-Forwarded-Proto: https`, the public https URLs.
- `user_oidc` (main, 8.12) takes every endpoint from that one discovery document,
  sends the browser to its `authorization_endpoint`, and refuses an ID token whose
  `iss` differs from the document's `issuer`. It has no setting for a second,
  internal set of endpoints; its only TLS option, `httpclient.allowselfsigned`,
  turns certificate validation off.
- From Nextcloud's container, Authentik's public name over https answers 403 on the
  closed policy, with a valid certificate (DEC-076: a closed route refuses every
  container).

So the browser leg can stay closed, and with the shipped model the server leg
cannot reach a closed Authentik: a discovery fetched over the Docker network hands
the browser an internal authorize URL, and one fetched at the public name is
refused. Split DNS alone does not change that — measured: with Authentik's name
resolving to Traefik on Nextcloud's edge network, the certificate validated and the
closed router answered 403.

**A private path, measured in the lab only (not in the repository).** Three runtime
changes, all reverted afterwards:

1. Traefik carried Authentik's canonical name as a network alias on
   `nextcloud-edge`, so the name resolved to Traefik there;
2. `nextcloud-app` joined `nextcloud-edge`;
3. a router admitted only Authentik's machine endpoints — `token/`, `userinfo/`,
   per application `.well-known/openid-configuration` and `jwks/` — and only from
   `nextcloud-edge`'s subnet.

| Check | Result |
|---|---|
| Discovery from `nextcloud-app`, certificate verified | 200; issuer and endpoints the canonical public URLs; JWKS 200 |
| `authorize`, flow pages, API from `nextcloud-app` | 403 |
| The same discovery from another stack's container over the public address, from the host | 403, 403 |
| `nextcloud-nginx`, on the same edge network | 200 — the rule admits the stack's edge members, not the app alone |
| Nextcloud's own HTTP client | refused at first: it pins DNS and blocks private addresses unless `allow_local_remote_servers` is true; `user_oidc` does not set the per-request exception |
| With that switch on for the run | a full login — Nextcloud's button, Authentik's password and TOTP stages from the loopback probe, the callback — and Nextcloud redeemed the code over the private router (token 200 from `nextcloud-app`); the session belonged to the Authentik user |
| Login flow v2 with that session | the client received an app password; WebDAV 207 |

The switch was removed after each run. It is the cost of this path for Nextcloud:
`allow_local_remote_servers` lifts the SSRF guard for every server-side request of
every app, not only for the IdP.

**What a decision has to weigh.**

| Variant | Public exposure | What it needs | Security consequence |
|---|---|---|---|
| A. Authentik public, as its example ships | the whole IdP | nothing | the IdP's login, MFA, rate limit and CrowdSec face the internet |
| B. Opt-in public route for the machine endpoints | `token`, `userinfo`, discovery, JWKS | a route file like Seafile's `onlyoffice-callback.yml` | metadata public; token endpoint guarded by client secret and code; the rest closed |
| C. Private path on the consumer's edge network (measured above) | none | Traefik aliases per IdP on consumer edge networks (render), the consumer's app container on its edge, a per-consumer router — an exception to DEC-076.4 for a narrow route | the consumer stack's edge members reach the machine endpoints; for Nextcloud, `allow_local_remote_servers` globally — which lifts its SSRF guard and is no candidate for a blueprint default |

For the clients, nothing in the choice changes the sync: an OIDC account has no

How to read it:

- "First document open" is the probe's first document that reached the editor's ready
  event, attempts every 15 s: OnlyOffice's cold starts fall on 10.5 s or 26 s by that
  step, not by a difference in the server. Each probe includes the harness start.
- Save is not the same act: OnlyOffice and Euro-Office from a forcesave command to the
  callback that delivers the file; Collabora from the save message to the WOPI PutFile.
- OnlyOffice's total includes 1.7 GB of file cache the kernel can reclaim; its
  anonymous memory is the lowest of the three at idle. Euro-Office forks about 180
  processes and holds most of its memory anonymously.
- All three stayed far below their limits (OnlyOffice and Euro-Office 4 GB, Collabora
  1.5 GB). An edit that "did not land" is the harness typing before the editor took
  focus; each was retried once and then saved.

disk and start time of the other two; OnlyOffice and Euro-Office open and save in about
two seconds and one, Collabora in under one and a fraction. They do not say anything
about large documents, many concurrent users, or format fidelity, which was not
compared; nor about the official clients.
