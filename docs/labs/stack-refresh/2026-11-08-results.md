**Capabilities the remaining families need at start** — measured with the upstream
image alone, `cap_drop: ALL` and `no-new-privileges`, a fresh data directory in the
image's own volume, the default entrypoint; first without any capability, then with a
candidate set (`CHOWN DAC_OVERRIDE FOWNER SETUID SETGID NET_BIND_SERVICE KILL SETPCAP
FSETID`) reduced one at a time while the service still answered its own client:

| Family (image measured) | `cap_drop: ALL` alone | smallest set that started and answered | the error without it |
|---|---|---|---|
| mariadb (`mariadb:12.3.3`) | fails | `SETUID`, `SETGID` | `failed switching to 'mysql': operation not permitted` |
| mysql (`mysql:8.4.13`) | fails | `DAC_OVERRIDE`, `SETUID`, `SETGID` | `setgid: Operation not permitted` |
| mongo (`mongo:8.0.34`) | fails | `SETUID`, `SETGID` | `failed switching to 'mongodb': operation not permitted` |
| memcached (`memcached:1.6.45-alpine`) | starts | none | — |
| nginx (`nginx:1.31.8-alpine-slim`) | fails | `CHOWN`, `SETUID`, `SETGID` | `chown("/var/cache/nginx/client_temp", 101) failed`, then `setgid(101) failed` |

`NET_BIND_SERVICE` was not needed for nginx's port 80: Docker sets
`net.ipv4.ip_unprivileged_port_start=0` in every container's network namespace.
Limits of this measurement: a bind mount owned by another user than the image's
needs `CHOWN` (and for mysql `FOWNER`) on the first start, as the READMEs' `chown`
steps show; an existing data directory was not measured; the stacks' own entrypoints,
where a stack replaces the image's, were not measured. Nothing in the stacks was
changed from these numbers.

## Management tools

`core/portainer` and `core/dockhand` on the lab host (VM), `core/portainer-agent` and
`core/hawser` in the lab container (LXC). Both agents reach their server through
Traefik, so the lab container had to be inside `TRUSTED_RANGES` — the stand-in for a
tailnet member. From stage 2 on, the roles of check 3 were swapped: the lab container
is the trusted client, the hypervisor host the refused one.

| | Portainer 2.45.3 → Edge agent 2.45.3 | Dockhand v1.0.57 → Hawser 0.2.53 (edge) |
|---|---|---|
| Path | the agent polls `https://<portainer>/` through Traefik and opens the tunnel to port 8000, published on one address of the VM (the lab's stand-in for the VPN address the README names), never `0.0.0.0` | Hawser connects out to `wss://<dockhand>/api/hawser/connect` through Traefik with its token |
| Secret | the Edge key; the Edge identifier had to be the one Portainer stores for the environment — with an identifier of the agent's own, the poll answered `invalid Edge identifier` | the token from `/api/hawser/tokens`, saved against the environment |
| Ports on the agent host | none published | none published |
| Seen from the VM | the lab container's containers listed | the lab container's containers listed |
| Actions | image pulled, a container created, started, its log read, stopped, removed | a log read, a container stopped and started |
| After the server's `down`/`up` | reconnected by itself | reconnected by itself |
| Local host | through `tcp://socket-proxy:2375` | through `socket-proxy:2375` |
| Setup | the administrator only with the setup token (the header `X-Setup-Token`; without it refused); past five minutes the setup locks until a restart, as the README says | **no authentication on a new instance** (`authEnabled: false`) — README corrected |

Version judgement: the upstream inventory marks `core/portainer-agent` as behind
(2.45.3 → 3.0.1). 3.0.1 is Portainer's short-term-support line (`sts`); the server is
pinned to the 2.45.3 LTS line, and agent and server have to match. Not moved — a false
comparison between an LTS pin and an STS release, not a finding.

The agents ran in an unprivileged LXC with nesting; nothing in either agent needed more.

### FA-12 — the Upgrade header in ERPNext's nginx

Checked on the running v16.54.0 frontend: `config/nginx-socketio.conf` and the
image's own `frappe.conf` set `Upgrade`/`Connection` only in their `location /socket.io`
blocks; `location /` hands over to `@webserver`, which sets neither, and nginx does
not pass hop-by-hop headers on its own. A request with `Upgrade: h2c` and
`HTTP2-Settings` to `/api/method/ping` was answered as plain HTTP/1.1 (`200`); the
websocket upgrade on `/socket.io` answered `101`. The path the finding describes does
not exist in this configuration, so nothing was changed. Traefik 3.7.13 and later do
not forward `Upgrade: h2c` either (`docs/audits/dependency-sweep-2026-09-13.md`).

### FA-03 — the PostgreSQL client, measured at three server majors

Both ways for every PostgreSQL stack that was rehearsed: **A** is the README's

recommends — `pg_dump_command: docker exec <db> pg_dump` for the dump,
`pg_restore_command`/`psql_command: docker exec -i <throwaway> …` for the restore, no

What else the runs showed:

- When A's `pg_restore` stops, borgmatic 2.2.0 reports only
  `'utf-8' codec can't decode byte 0xb9 in position 3: invalid start byte`; the real
  error appears only with `-v 2`. An operator reading the default output would not
  learn that the client is the cause.
- C needed no credential and no address: the official images trust the local socket.
  The restore target has to be running before `borgmatic restore`, exactly as for A.
- The dump through C ran inside the database container's limits; none of these
  databases came near them.
- A row count taken while the application still writes can differ from the dump by a
  few rows (Zammad, Lychee); a second count after the restore matched exactly. The
  comparison belongs right after the dump, or with the application stopped.

C was the only way that worked for all three majors. Nothing in the repository was
changed; the decision is open (`ROADMAP.md`, FA-03).

## From zero to a running host

What the path from an empty Debian 13 machine to Traefik, CrowdSec and the first
stack was, in order:

1. Docker from Docker's repository and the daemon settings — `docs/host-baseline.md`
   lists them as a table of what the earlier host had, not as steps; the order
   (address pools before the first network) is only in SHOULD 5.
2. `core/traefik`: `cp .env.example .env`, then the choices of the setup table.
   For an IPv4-only host the README said to drop the overlay and empty
   `TRAEFIK_BIND_V6`; `validate.sh` still refused the shipped example
   `PUBLIC_NETWORK_SUBNET_V6` — corrected in the README and `.env.example`.
3. `ACME_EMAIL` is required by `validate.sh`; Let's Encrypt no longer needs an
   address, and an `example.com` address is refused by Let's Encrypt, so an
   operator needs a real or at least a resolvable domain here.
4. There is no switch for Let's Encrypt staging; the staging run needed a hand
   edit of the rendered `config/traefik.yml` (`caServer`), which the next
   `render.sh` removes.
5. The Cloudflare token worked with `Zone → DNS → Edit` alone, scoped to the one
   zone; `Zone → Zone → Read` was not needed for the zone lookup.
6. `core/crowdsec`: setup as written; step 5 (`ops/allowlist.sh apply`) failed until
   the fix above.
7. The bouncer: key, `.env`, `render.sh`, `--force-recreate` — as written.
8. The first stack (`apps/whoami`) needed `APP_TRAEFIK_ACCESS=access-trusted`: the
   shipped `access-vpn` refuses every client on a host without a VPN.

## Suggestions for coordination

Nothing here is implemented; each needs a decision or belongs to the coordination.

1. **A checker for first-visitor takeover.** Six stacks shipped `access-public` while
   the first visitor became the administrator or a default administrator logged in
   (OpnForm, Immich, Lychee, Zammad, authentik, BookStack — corrected here), the pattern listmonk and Ghost showed on the earlier
   host. `check-baseline.py` could require `access-vpn` (or an explicit, reasoned
   exception) for a stack whose README or UPSTREAM.md names a first-run setup page.
   The stacks of stage 4 were not reached; a rule would find the rest.
2. **A check that a digest pin is the digest of the tag beside it.** `business/vikunja`
   named `2.6.0` and built `2.3.0` for every install; `upstream-status.py` reports a
   locally built stack only as _not determinable_. All other digest pins were checked
   by hand in this run and match their tags; `business/akaunting`'s `3.3.0-v` was
   rebuilt upstream since its pin (pinned `6c5e9864dfe7`, the tag now `72875c110a66`) —
   not wrong, but a re-pushed tag the weekly job could report.
3. **FA-03.** The measurements above are the basis asked for: option C worked for
   14, 16 and 18, option A failed for all three. The rehearsal rows that ran only C say
   so and do not count as a passing restore.
4. **`scripts/ci/test_traefik_render_identity.py` fails in a live checkout.** It copies
   `core/traefik/` including the untracked, rendered `config/` of a running install and
   then refuses to render; in a clean worktree it passes. The test could copy tracked
   files only (`git ls-files`), so the CI checks can be run on a deployed host.
5. **A Let's Encrypt staging switch in `core/traefik`.** The staging run needed a hand
   edit of the rendered `traefik.yml`; an `ACME_CA_SERVER` variable in the template
   would make the documented "staging first" practical. And `ACME_EMAIL` is required by
   `validate.sh` although Let's Encrypt no longer needs it — a decision whether it stays
   required.
6. **`borgmatic` reports a failed `pg_restore` as a UTF-8 decode error.** Worth a line in
   `backup/borgmatic/RESTORE.md` ("run with `-v 2` when a restore fails") until FA-03
   is decided — and possibly an upstream report.
7. **One-off commands inside containers that read secrets in an entrypoint.**
   `paperless-ngx` (`createsuperuser --noinput` under `exec -e` silently creates a user
   without a usable password, because the image's `with-contenv` replaces the
   environment) and `openproject` (`rails runner` under `exec` lacks
   `SECRET_KEY_BASE`; through the entrypoint inside `web` it pushed web past its 1G limit,
   three OOM kills) both need a documented way; for OpenProject
   `docker compose run --rm --no-deps seeder <command>` worked.
8. **`business/openproject` limits.** Web peaked at its 1G limit only while a console
   ran inside it; the seeder and worker were raised to the smallest working step (1G).
   The real numbers need a steady-state and load measurement.
9. **Upgrades not run here, worth a host session:** `apps/paperless-ngx` from
   Postgres 16 to 18 and `apps/nextcloud` from 34 to 35 on existing data — both pins
   moved before this run and are verified here as fresh installs only.
10. **`apps/collabora`: `/cool/convert-to` is an open conversion service (High).**
    A POST from the refused client — outside `TRUSTED_RANGES`, on the public router —
    came back as a PDF. coolwsd's `net.post_allow` sees only Traefik's private address,
    so its default private-range list admits everyone behind the proxy. Closing it (a
    second router for `PathPrefix(`/cool/convert-to`)` at `access-trusted-vpn` or
    `access-blocked`) needs a decision, because Nextcloud's office integration may use
    the endpoint for previews; not checked here.
11. **`upstream-status.py` and pre-releases.** n8n 3.1.0 (a GitHub pre-release) and
    Portainer's STS 3.0.1 were reported as the newest release over stable or LTS pins.
    Reading the `prerelease` flag, and the LTS/STS channel where upstream names one,
    would remove both false "behind" rows.
12. **Root without `DAC_OVERRIDE` and the README's `mkdir`.** `apps/nocodb` runs as root
    with `cap_drop: ALL`; a data directory created by the operator's user is then not
    writable. Other stacks that run as root without capabilities and bind a directory
    the README creates may have the same gap; `check-baseline.py` could flag
    `cap_drop: ALL` without `user:` on a service with a writable bind mount.
13. **"200 OK" in verify steps of stacks with a setup page.** Homarr and Uptime Kuma
    redirect a new instance to their setup; the verify lines said 200 (corrected). The
    same wording may be elsewhere.
