# Stack refresh, 2026-11-08: results

Every stack is at the newest upstream release or names why not, starts with the files it
ships, and ships closed. 120 of the 121 stacks are verified on a host and 109 of the 114
local files run. This report holds the evidence per stack: the checks, what was fixed, the
measured capabilities, memory peaks and restores. The local files are in
[`2026-11-08-local-stacks.md`](2026-11-08-local-stacks.md).

## Summary

- **120 of 121 stacks verified on a host.** Each passed the five checks of
  [`docs/host-session-priority-1.md`](../../host-session-priority-1.md): it starts healthy,
  answers through Traefik with a certificate, refuses an unauthorised client, passes its
  README's smoke test, and comes back after `down`/`up`. `core/traefik` keeps its line of
  2026-11-01, which also covers dual-stack and outside access. Not verified: `apps/vllm`,
  which needs a GPU.
- **32 stacks at a newer pin**, among them two majors (`apps/docker-mailserver` 17,
  `monitoring/zabbix` 8.0 LTS), and Silo in place of the withdrawn MinIO image in two stacks.
  Where a pin is not the newest upstream tag, the table names why.
- **62 faults fixed**: routes that let the first visitor take over now ship closed;
  containers that could not write their own directories start; a withdrawn image is
  replaced; an open conversion service is closed; the watchdogs recover as described; a
  placeholder no longer opens an admin panel.
- **Measured and in the compose files**: capabilities for nine services, memory limits for
  twenty-one, the PostgreSQL dump with the server's own client (FA-03) in 25 READMEs.
- **Thirteen restores**, each with identical row counts per table.
- **After a reboot**, every container is back within 58 s.

## Collabora behind Nextcloud's closed route

`/cool/convert-to` is closed on Collabora's public route: a second router of
higher priority answers it with `access-blocked`. The path converts any uploaded file
without a WOPI token, and Collabora admits it from private addresses — Traefik included.

Tested with Nextcloud 35.0.2 behind `access-trusted` and a headless Chromium: a `.docx` opened, was edited, saved and reopened four times, and the text was
in the file read back over WebDAV. Two things were needed, both now in the repository:

1. **The template presets.** Collabora fetches them at the URLs Nextcloud writes into
   its settings response. With `OVERWRITEHOST` applied to every request those pointed
   at the closed public name; the document did not open (`Failed to fetch preset … Forbidden`).
   `NC_OVERWRITECONDADDR` — the regex of Nextcloud's edge subnet — limits the overwrites
   to requests from Traefik; a callback over nginx gets URLs at nginx. This closes the
   finding the Nextcloud README recorded as open.
2. **Previews.** The `.docx` preview broke with the closed path, as expected (Nextcloud
   called `convert-to` at the public name: `403`). `office-collabora.yml` gives
   Nextcloud an internal address instead: nginx, already on Collabora's edge network,
   passes discovery, capabilities and `/cool/convert-to` on port 9980. PHP-FPM stays off
   that network. Previews then rendered (`200 image/png`).

`/cool/convert-to` answered `403` to the trusted and the refused client, before and after
`down`/`up` of both stacks.

## Host watchdogs

Both scripts, installed from the host-files manifest, with Healthchecks as the receiver:

| Rehearsal | Docker daemon watchdog | Traefik watchdog |
|---|---|---|
| Fault | `dockerd` frozen (`SIGSTOP`): process alive, API hanging | Traefik frozen; `unhealthy` after 40 s |
| Confirmation | "streak 1/3", "2/3", restart on the third run | restart on the third unhealthy check |
| Result | "daemon now responding"; all ten containers running 58 s after the first run | "restarted after 3 unhealthy checks, now healthy" |
| Escalation (restarted service frozen again at once) | after the fixes: escalated after 35 s, the next run reported failure without another restart | after the fix: one restart, `escalated`, no further restart; healthy again after the process resumed |

Three faults are fixed:

- The Traefik watchdog took `starting` after its restart for success. A restart that did
  not help reset the episode, and the next confirmation restarted Traefik again — the
  endless retry the README rules out. Only `healthy` counts now (`START_TIMEOUT`).
- The Docker watchdog waited without limit in `systemctl restart docker` for a daemon that
  hung while starting (`docker.service` has no start timeout) and sent no ping.
  `RESTART_TIMEOUT` bounds it.
- Its unit was ordered after `docker.service`, so every later run queued behind the hanging
  start job. The ordering is gone.

In one of three double faults Traefik alone stayed `Exited (137)` after the daemon came back
and needed `up -d`; the watchdog checks the daemon, not the containers (recorded in its
README). The watchdogs reach a Healthchecks on the same host at `127.0.0.1:8001`: through
Traefik a request from the Docker host arrives as `proxy-public`'s gateway, which a closed
policy refuses and `validate.sh` keeps out of `TRUSTED_RANGES`.

## Restart test

The host was rebooted twice with `core/traefik`, `core/crowdsec`, `core/portainer`,
`core/dockhand` and `apps/whoami` running. Every container came back through
`unless-stopped`; check 3 passed for all three routes. Measured from the reboot command:

| What | back after (first / second reboot) |
|---|---|
| SSH | 30 s / 44 s |
| `apps/whoami` through Traefik with a valid certificate | 39 s / 58 s |
| `core/portainer` API | 40 s / 54 s |
| `core/dockhand` | 46 s / 58 s |
| Hawser on the agent machine | connected again without action, both times |
| Portainer's Edge agent | without action the first time; the second time its poll kept failing for about six minutes after Portainer answered, until the agent container was restarted |
| CrowdSec bouncer | pulling, as a new entry `traefik-bouncer@<new address>` beside the stale one, as `core/crowdsec/README.md` describes |

A host without a firewall needs no `nftables-no-flush.conf` drop-in.

## Setting up a new host

What an empty Debian 13 machine needs before Traefik, CrowdSec and the first stack, and
what the documentation says about it:

1. Docker from Docker's repository and the daemon settings. `docs/host-baseline.md` lists
   the settings as a table, not as steps; that the address pools come before the first
   network is only in SHOULD 5. Docker's default pools include `192.168.0.0/16`, which can
   overlap a LAN. **Open.**
2. `core/traefik` on an IPv4-only host: `validate.sh` refused the shipped
   `PUBLIC_NETWORK_SUBNET_V6`. **Fixed** in the README and `.env.example`.
3. `ACME_EMAIL` is required by `validate.sh`, and Let's Encrypt refuses an `example.com`
   address, so an operator needs a real or at least resolvable domain there. **Open.**
4. There is no switch for Let's Encrypt staging; a staging run needs a hand edit of the
   rendered `config/traefik.yml` (`caServer`), which the next `render.sh` removes. **Open.**
5. The Cloudflare token works with `Zone → DNS → Edit` alone, scoped to the one zone;
   `Zone → Zone → Read` is not needed.
6. `core/crowdsec`: setup as written; `ops/allowlist.sh apply` works since `fc6092d8`.
7. The bouncer: key, `.env`, `render.sh`, `--force-recreate`, as written.
8. The first stack ships `access-vpn`, which refuses every client on a host without a
   VPN; such a host sets `access-trusted` with its ranges.

## Open

What does not work yet, or is not checked automatically:

1. **A container running as root with `cap_drop: ALL` cannot write what the operator
   owns.** NocoDB, Velociraptor, ShellHub, Orion-Belt, Teleport and UrBackup failed this way
   (fixed). No check flags `cap_drop: ALL` without `user:` on a service with a writable bind
   mount or a mode-600 secret.
2. **The local headers can drift from the README.** Twenty-four lacked its `chown` steps
   (fixed); no check compares the two.
3. **An undefined `@file` reference drops the router.** `apps/unifi` named a servers
   transport Traefik does not define (fixed); no check catches it.
4. **A digest pin can differ from its tag.** `business/vikunja` built 2.3.0 while naming
   2.6.0 (fixed); `business/akaunting`'s `3.3.0-v` was pushed again upstream since its pin.
   No check compares them.
5. **After `systemctl restart docker` some `unless-stopped` containers stay down**
   (Traefik, a Dockhand database, Portainer); a reboot brings everything back. The Docker
   watchdog checks the daemon, not the containers.
6. **Two clashes on one host:** `core/jumpserver` and `core/orion-belt` both publish `2222`;
   `monitoring/beszel` and `monitoring/beszel-agent` both name a container `beszel-agent`
   (by design for different hosts). Neither README says so.
7. **OpnForm's nginx resolves its upstreams once.** Recreating only `opnform-ui` leaves `/`
   at `502` until nginx restarts.
8. **borgmatic reports a failed `pg_restore` as a UTF-8 decode error**; the real error
   shows only with `-v 2`.
9. **One-off commands in containers whose entrypoint reads secrets** (Paperless,
   OpenProject) have no documented way.
10. **The render-identity unit test fails in a live checkout**: it copies the untracked
    rendered `config/`.
11. **Many large stacks starting at once** on one host stall on disk I/O before memory:
    with fourteen pulling at once containerd timed out, and about twenty running at once
    exhausted 18 GiB. Two to four at a time worked.
