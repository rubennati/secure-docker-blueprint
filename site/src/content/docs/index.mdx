Starting a container is one command. Keeping the service reachable only to the
people who should reach it, patched, and recoverable when the disk goes — that
is what these guides are about.

## Start with one of these

Each of these runs on your own machine with Docker and nothing else — no proxy,
domain or certificate, and none of the protection a server gets. The secrets ship
empty; each block fills the ones its stack requires. Clone once, then run a block
from the repository root:

```bash
git clone https://github.com/rubennati/secure-docker-blueprint.git
cd secure-docker-blueprint
```

Nextcloud and Vaultwarden both answer on port 8080: stop one with `down` before
starting the other.

<Card title="Nextcloud" icon="laptop">
  Files, calendars and contacts on your own server, synced to desktops and phones.

  ```bash wrap
  cd apps/nextcloud
  cp .env.local.example .env.local
  for v in DB_PASSWORD DB_ROOT_PASSWORD REDIS_PASSWORD ADMIN_PASSWORD; do
    echo "$v=$(openssl rand -hex 16)"; done >> .env.local
  mkdir -p volumes/local/mysql volumes/local/redis volumes/local/html
  sudo chown 999:999 volumes/local/mysql
  docker compose -f docker-compose.local.yml --env-file .env.local up -d
  ```

  Open `http://localhost:8080` and log in as `admin`; `grep '^ADMIN_PASSWORD=.' .env.local`
  prints the password. [Nextcloud guide →](/applications/nextcloud/)
</Card>

## What is claimed about testing

Each guide opens with its evidence line: *Last run on a host* with the date and
the version that ran, *data restored from a backup* where that happened, the
pinned version with what upstream has released since, and the findings the
upstream images carry. The line states facts; it grades nothing.
